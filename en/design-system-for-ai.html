How to prepare a design system to work with AI tools

An AI that codes interfaces does not know your buttons or your colours: if you do not give them to it, it invents others. Preparing the design system means giving it that context in a form a machine can read.

In short
  • Without context, an AI builds interfaces from what it knows from the internet, not from your components. The design system is that context.
  • It has three layers: tokens (the decisions: colours, sizes, type), components (the pieces) and documentation (when to use each one).
  • Name by use, not by look: “color.action” survives a rebrand; “dark-green” does not.
  • Since 2025 there has been a stable format for tokens and, since 2026, Figma and Storybook expose the system to AI agents.

If you ask an AI to “make me a contact page”, it will make one. With its own buttons, colours and margins, which are not yours. That is not a fault: nobody told it which ones are yours.

This is the conversation I see most right now among design and development people. And the answer is almost always the same: the design system is no longer only for humans.

Why does AI invent components?

The Storybook team puts it bluntly: agents know nothing about your components, so they generate code that does not match your standards. And a real design system, with its variants and rules, is too big to paste whole into a prompt.

The solution is not to write longer instructions. It is to have the system in a format the tool can look up when it needs it.

Which three layers does it need?

1 · TokensThe decisionsColours, typefaces, spacing, radii. Each value with a name.
2 · ComponentsThe piecesButton, field, card, alert. With their variants and states.
3 · DocumentationThe rulesWhen each piece is used, when it is not, and an example of each case.

How should tokens be named?

A token is a named value. The key is for the name to say what it is for, not what it looks like:

In October 2025 the W3C Design Tokens Community Group published the first stable version of its specification: a common JSON format for passing tokens between tools. If you start today, store them in that format and you will not have to redo them.

How many components do you need?

Fewer than you think, but complete. A component is complete when it has:

  • Named variants: primary, secondary, text. Not “button 2”.
  • Every state: default, hover, keyboard focus, disabled, loading, error.
  • The same name in design and in code. If it is “Card” in Figma and “Box” in the code, the AI does not know they are the same thing.

Eight well-made components are better than forty half-finished ones. Where pieces are missing, the AI improvises.

What needs documenting?

What you would explain to someone new on the team, in writing and next to the component:

Write it down
  • What it is for, in one sentence
  • When to use it and when not to
  • One good example and one bad one
  • Which options it accepts and which do not exist
  • Accessibility requirements
Not needed
  • The history of why it was done this way
  • Screenshots with no text explaining them
  • Rules nobody follows
  • The same thing repeated in three places

Rules in text are what a machine reads best. A beautiful image of “how to use the logo” is of little use to it.

Where does AI read it?

  1. In the designFigma’s MCP server passes variables, components and their measurements to coding tools. With Code Connect, it also tells them which code component matches each piece.
  2. In the codeIn 2026 Storybook added an MCP server (for React, for now) that gives agents the real components, their options, their documentation and their tests, so they reuse instead of inventing.
  3. In a rules fileA short text in the project with the essentials: tokens, available components and what is never done. It is the minimum and works with any tool.

For exploring ideas before you get here, read Google Stitch and Figma: what AI speeds up.

What if my business is small?

Then your design system fits on one sheet, and that is already much more than most have:

  1. Three or four coloursWith their code and what each one is for.
  2. Two typefacesOne for headings and one for text.
  3. What your buttons and cards look likeCorners, size, one example.
  4. Your toneThree sentences you would say and three you would not.

With that sheet, any AI tool (and any person) will make things that look like you. If you are not sure whether you need a touch-up or a fresh start, see rebrand or brand refresh.

Frequently asked questions

What is a design system?

It is the set of visual decisions for a product (colours, typefaces, spacing), the pieces built from them (buttons, fields, cards) and the rules for using them. It keeps everything that is designed and coded consistent.

What are design tokens?

They are design decisions stored as named values: for example, “color.action = #004833”. Since October 2025 there has been a stable specification from the W3C Design Tokens Community Group for sharing them between tools.

Do I need Storybook to work with AI?

It is not required. It helps if your product is built with React and your components are already documented there. If not, a rules file in the project and a well-organised design in Figma already improve the result a lot.

Does a small business need a design system?

Not a full one. One sheet with its colours, typefaces, examples of buttons and cards, and its tone is enough for any person or tool to make things that are consistent with the brand.
